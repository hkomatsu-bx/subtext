# リスクとセキュリティ方針

楽観的な見立てを避け、ダウンサイドを明示する。

## 法務とコンプライアンス

会議に参加せず通知も出さないため、実質的に秘密録音になる。
製品化の前に法務確認をゲート条件とする。

- 日本では当事者録音は原則適法とされるが、これは一般論であり弁護士見解ではない（確信度：中）。
- 社内規程や顧客との NDA に抵触する可能性がある。
- 海外参加者がいる会議では、全当事者の同意を要する地域（米国の一部州など）の法律に触れうる。
- 相手を個人単位で識別・記録する機能、特に声紋による自動命名は生体情報に当たる。個人情報保護法（個人識別符号）や海外の生体情報規制（米イリノイ州 BIPA など）で保護が強い。

対応方針は、事前告知を前提とする運用設計とし、製品化前の法務確認をゲートに置くことである。
声紋自動命名はこの確認を前提とし、現時点では実装しない。

## 技術リスク

- 話者分離の品質が Amazon Transcribe に一本化されている。日本語バッチが期待を下回った場合、手元に代替がない。逃げ道はレンタルのクラウド GPU による代替処理で、将来検討とする。
- ループバックは無音時にデータを出さないことがあり、2 系統の同期がずれうる。Unit A の絶対時刻アンカー同期（BR-SYNC）で補正する。
- 通知音や他アプリ音の混入がある。クリーンな取得にはプロセス別ループバックが要るが、ネイティブ補助を要するため対象外とした。ユーザー運用で抑える前提を採る。
- A1 の fail-fast 反転は設計の根幹に触れ、欠落区間の扱いと重複字幕に新たな複雑性を生む（確信度：高）。再接続の境界は表示で明示するだけで、重複 final の除去は実装していない。
- ライブ議事録（B1）は LLM 呼び出しの頻度がコストに直結するため、間隔設計を要する。

## コスト

- ライブ（ストリーミング）と会議後（バッチ）で、同じ音声に 2 回の文字起こし課金が発生する。ライブ字幕が不要な運用ならバッチのみに寄せて削減できる。
- 要約は Bedrock の従量課金である。
- 変動費は会議時間と回数に比例する。ボット単位の従量課金やローカル GPU の設備投資は不要という優位がある。
- 会議ハーネスは実行のたびに概算を台帳に記録し、閾値超過を警告する（[06-会議ハーネス.md](06-会議ハーネス.md) を参照）。金額は概算で、正は AWS Cost Explorer とする。

## セキュリティの基本姿勢

音声・PII はローカルまたは自社 AWS に留め、外部へ出さないのが基本方針である。
自分専用の実用段階で、この姿勢を明示的に決め直した（決定：2026-06-24）。

- **ローカル永続化を許可する**（ローカルのみ）。Unit C の非永続を定めた BR-SEC-03 と BR-RENDER-01 を、ローカル保存に限って上書きする。外部送信は AWS のみに維持する。これによりライブ議事録（B1）とその永続化（B1F）が成立する。
- **カスタム語彙の AWS アップロードを許可する**。これにより C1 が成立する。
- **Slack への外部送信を明示的に拡張する**（H2）。送るのは要約本文に限り、投稿ごとに事前承認する。

一方で、次のセキュリティ規則は一貫して守る。

- 認証情報をソースコード・設定に直書きしない（BR-SEC-01、NFR-SEC-07）。環境変数・AWS プロファイル・SSO で解決する。
- ログに音声内容・実名（PII）・認証情報を出さない（NFR-SEC-04）。
- S3 は保存時暗号化・パブリックアクセス遮断・TLS 強制（NFR-SEC-01／03）。
- IAM は Transcribe・Bedrock・対象 S3 に限定する（NFR-SEC-02）。Transcribe だけは ARN で絞れないため `*` が残る（[07-インフラ設計.md](07-インフラ設計.md) を参照）。
- 依存はロックファイルまたは正確なバージョンで固定し、公式レジストリのみを使う（NFR-SEC-05）。

Claude 生成経路（`--no-summarize`）は、実名入りトランスクリプトが Anthropic 側へ送信される点で Bedrock 経路と決定的に異なる。
この経路の選択はガバナンス判断のうえで行い、PII を社外に出さない運用では Bedrock 経路を既定とする。
