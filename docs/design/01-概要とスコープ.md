# 概要とスコープ

## Subtext とは何か

Subtext は、Web 会議の音声を文字起こしし、会議後に議事録を自動生成する Windows 向けツールである。
プロダクト名は「行間を読む（subtext）」と「テキストを生成する」の両義を一語に込めた。

既存の同種サービスの多くは、会議にボットを参加させて音声を取得する。
Subtext はボットを参加させず、PC 上で再生される会議音声を OS の音声層から直接取得する。
会議アプリではなく OS の音声を取るため、Zoom・Teams・Google Meet など出力先を問わず同じ仕組みで動く。

音声認識と要約はクラウド（AWS）の Amazon Transcribe と Amazon Bedrock（Claude）で行う。

## 背景と課題

議事録の作成は手間が大きく、自動化の需要は高い。
既存の自動議事録サービスの多くはボット参加方式を採り、この方式には次の弱みがある。

- 参加者一覧にボットが現れ、相手に録音を強く意識させる。
- 会議プラットフォームごとに連携実装や対応可否が分かれる。
- ボット 1 台ごとの従量課金が発生する場合がある。
- ボットの追加が禁止された会議では使えない。

## 提案するプロダクト

会議に参加せず、PC のスピーカー出力（相手の声）とマイク入力（自分の声）を OS の音声層で取得して記録する。
会議中はリアルタイム字幕を、会議後は構造化された議事録（決定事項・ToDo・論点）を生成する。
動作環境は Windows である。

## 差別化：なぜ参加しないか

価値の中心は、会議に参加しないことで生まれる次の 4 点にある。

- **プラットフォーム非依存**：会議アプリの API に依存せず、音声を出すアプリはすべて対象になる。
- **非侵襲**：参加者一覧にボットが出ない。相手の警戒や心理的負担を生まない。
- **コスト**：ボット単位の従量課金がない。
- **適用範囲**：ボット追加が制限された会議でも記録できる。

「参加しない、つまり相手に通知されない」点は、法務リスクと表裏である（[09-リスクとセキュリティ方針.md](09-リスクとセキュリティ方針.md) を参照）。

「非参加」は本プロダクトが死守する性質である。
サーバ側でボットを会議に参加させる方式や、別アカウントを会議に増やす方式は採らない。

## ターゲットと利用シーン

- 社内会議の議事録自動化。
- 顧客折衝やヒアリングの記録と要約。

実現方式が AWS ネイティブのため、AWS を基盤とする組織では既存のガバナンスに載せやすい。

## スコープと前提

### 対象

当初は技術的実現可能性の検証（PoC）を対象とし、最も不確実な 2 点を最優先で検証した。

- WASAPI ループバックの実用性：相手の音声を、会議に参加せずクリーンに取得できるか。
- 日本語バッチ話者分離の品質：会議後処理で相手の個人を実用的に区別できるか。

この 2 点はいずれも検証を通過した。
その後、自分専用の実用ツールとして堅牢性・機能・精度を高める段階に入り、再接続耐性（A1）・用語精度（C1／C2）・対話駆動オーケストレーション（H2）を実装した。

### 想定規模

想定する会議規模は相手 5 名までである。
話者分離が精度を出す 2〜5 名の範囲に収まる（NFR-02、FR-08）。

### 対象外

次はプロダクト化の基盤に属し、現時点の対象外とする。

- マルチテナント・認証権限・課金基盤。
- 配布インストーラ・クロスプラットフォーム対応。
- 声紋による自動命名。生体情報に当たり、法務確認を前提とする。
- プロセス別ループバック（特定アプリの音だけを取るクリーン化）。ネイティブ補助を要する。

### 実装言語と環境の前提

言語構成は音声経路とクラウド処理経路で分割する（NFR-03）。
リアルタイム音声経路（キャプチャ・録音・ライブ字幕）は C#（.NET、NAudio 参照）、会議後のクラウド処理経路（文字起こし・話者ラベル・要約）は Python である。

音声キャプチャ層はネイティブ Windows で動かす（NFR-04）。
WSL からホストの出力ミックスをループバック取得する確実な方法がないため、キャプチャ層を WSL 内には置けない。
Python 側の会議後処理は WSL やクラウドで動かしてよい。

AWS リージョンは東京（ap-northeast-1）で運用する（NFR-07）。

当初計画では Python を 3.11 または 3.12 に固定していた（3.13 系に一部ライブラリの不具合報告があったため。確信度：中）。
現行実装は uv workspace で Python 3.13 へ移行済みで、懸念した不具合は本プロジェクトの依存では現れていない。
C# 側のビルドターゲットも当初の `net8.0-windows` から `net10.0-windows` へ移行した（実行環境が .NET 10 SDK のみのため）。
