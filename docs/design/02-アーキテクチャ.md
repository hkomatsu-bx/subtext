# アーキテクチャ

## 3 ユニットの疎結合構成

システムは 3 つのユニットに分かれる。
それぞれ責務・言語・外部依存が異なり、独立して開発・実行できる。

| ユニット | 責務 | 言語 | 外部 AWS 依存 |
|----------|------|------|----------------|
| **Unit A** 音声キャプチャ／録音 | マイクとループバックの 2 系統を同期録音し、WAV とメタを保存する | C#（net10.0-windows） | なし |
| **Unit B** 会議後パイプライン | 文字起こし・話者分離・要約を行い議事録を生成する | Python 3.13 | S3・Transcribe（バッチ）・Bedrock |
| **Unit C** ライブ字幕 | 会議中のリアルタイム字幕を出す | C#（net10.0-windows） | Transcribe（ストリーミング） |

ユニット間は保存ファイルの受け渡しだけで連携する（FR-16）。
共有ライブラリも共有設定も持たない。
この疎結合により、あるユニットの内部実装を変えても、連携契約（ファイルの形式）を守るかぎり他ユニットに波及しない。

## データフロー

データは一方向に流れ、循環しない。

```
マイク / システム出力
  │
  ▼
Unit A 録音（C#, WASAPI）
  self.wav / others.wav / *.meta.json / manifest.json
  │  （ファイル受け渡し・言語境界 C#→Python）
  ▼
Unit B 会議後パイプライン（Python）
  文字起こし → 話者分離 → 統合 → 実名割当 → (補正) → 要約
  │
  ▼
final_transcript.json / minutes.md
```

Unit C はこの流れとは独立して動く。
会議中に Unit A・Unit B とは別の経路でリアルタイム字幕を出す。
既定では保存ファイルを介さないが、B1F を有効化した場合のみ確定字幕を JSONL に永続化し、Unit B への 4 つめの入口になる。

Unit A と Unit C は、音声取得の C# クラスライブラリ（capture）をビルドレベルで共有する。
これはコードの共有であって、実行時のデータや設定の共有ではない。

## 4 つの入口

議事録の生成には 4 つの入口があり、いずれも同じ「話者名の確認 → 要約」段に合流する。

- **録音経路**：Unit A で録音した `manifest.json` を Unit B の `paired` モードに渡す。主経路である。
- **WebVTT 直接**：会議サービス（Teams 等）が出力する字幕ファイルを Unit B の `vtt` モードに渡す（FR-17）。録音と Transcribe を経ない。
- **録画 mp4 → VTT**：録画から独立ツール `subtext-mp4-to-vtt` で WebVTT を生成し（FR-18）、WebVTT 経路に合流する。
- **ライブ字幕 JSONL → VTT**：Unit C が B1F で永続化した確定字幕を独立ツール `subtext-live-to-vtt` で WebVTT に変換し（FR-B1F-05）、WebVTT 経路に合流する。

WebVTT 経路は Transcribe と S3 を使わない。
`--no-summarize` を付ければ Bedrock も呼ばず、AWS 課金ゼロの完全ローカル処理になる。
この場合、議事録の文章化は Claude Code 側に委ねられる。

## ユニット間連携契約（FR-16）

ユニット境界を越えるのは、次のファイルだけである。
言語境界（C#↔Python）を越えるのは、Unit A から Unit B への録音成果物と、Unit C から Unit B へのライブ字幕 JSONL である。

| ファイル | 生成元 | 消費先 | 契約 |
|----------|--------|--------|------|
| `self.wav` / `others.wav` | Unit A | Unit B | 16kHz / mono / 16bit PCM（BR-FMT-01, BR-IN-04） |
| `self.meta.json` / `others.meta.json`（SidecarMeta） | Unit A | Unit B | `streamRole`・`startTimeUtc`・`deviceName`・`silenceFilledSec` など |
| `manifest.json`（RecordingManifest） | Unit A | Unit B | `sessionId`・`streams`（SidecarMeta ×2）・`status`・`commonStartUtc`。Unit B の主入口 |
| `live_captions.jsonl`（ライブ字幕） | Unit C（B1F 有効時） | `subtext-live-to-vtt` | 確定字幕を 1 行 1 JSON で追記。`offsetMs`・`source`・`speaker`・`text`・`captureUtc`（BR-B1F-IO-01） |
| WebVTT | 外部 / `subtext-mp4-to-vtt` / `subtext-live-to-vtt` | Unit B | `vtt` モードの入口（FR-17／FR-18／FR-B1F-05） |
| `speaker_names.json`（SpeakerNameMap） | 人手編集 | Unit B（内部） | 話者ラベルから実名への対応（BR-NAME-01） |
| `final_transcript.json`（FinalTranscript） | Unit B | Unit B（要約段）／外部（Claude Code） | 最終トランスクリプト。camelCase・enum 文字列で Unit A 出力と整合 |
| `minutes.md`（議事録） | Unit B | 最終成果物 | 決定事項・ToDo・論点を含む日本語 Markdown |

JSON の表記は camelCase に固定し、enum は文字列（`self`／`others`、`complete`／`incomplete`）で表す。
これにより C# 側の出力と Python 側の入力が同じ形で対応する。

## オーケストレーション

3 ユニットの実行を 1 か所から駆動するのが会議ハーネス `meeting` である。
ハーネスは各ユニットを subprocess で呼び、ユニット契約には踏み込まない。
CLI 本体は標準ライブラリのみで動き、TUI だけが Textual に依存する。
段の進行はファイルの存在で検知する。
詳細は [06-会議ハーネス.md](06-会議ハーネス.md) を参照する。

## 入出力レイアウト

録音・議事録の入出力はリポジトリルートの `data/` に集約する。
録音は `data/recordings/<session>/`、議事録は `data/out/<session>/` に置く（いずれも gitignore）。
設定（`.env`）はルート 1 か所に置く。
ハーネスは Unit B の実行時に `OUTPUT_DIR=data/out` を注入し、段検知と出力先を一致させる。
