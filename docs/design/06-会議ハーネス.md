# 会議ハーネス（meeting）

会議ハーネス `meeting` は、録音から議事録・Slack 投稿までの駆動をターミナル起点に寄せるオーケストレータである。
`tools/meeting`（uv workspace のメンバー、CLI 名 `meeting`）に置く。
リポジトリルートから `uv run meeting ...` で呼ぶ（workspace 化により cd 不要）。

## 位置づけと原則

ハーネスは各ユニットを subprocess で呼ぶだけで、ユニット契約（FR-16）には踏み込まない。
CLI 本体は依存ゼロで標準ライブラリのみで動く（Slack 投稿も標準ライブラリの HTTP で直接行う）。
TUI（`meeting tui`）のみ Textual に依存する（`pyproject.toml` の必須依存）。
段の進行はファイルの存在で検知する。

パスや TargetFramework はコードに直書きせず、`meeting.toml` の `[paths]` とビルド出力探索で解決する。
これにより別 PC・別構成へ移植できる。
録音実行ファイルは self-contained publish 出力（`dist/recorder`）を優先し、無ければ開発ビルド出力を探索し、それも無ければ自動でビルドする。
ライブ字幕（`dist/live`）も同じ解決規則に従う。
開発ビルド出力を使う場合は、実行ファイルが存在しても `csproj` の更新時刻が実行ファイルより新しければ再ビルドする（配布成果物は対象外）。

Unit B の起動は `uv run subtext-postmeeting` の一本とし、録音・ライブ字幕のような dist 経路は設けない。
ハーネス自体が `uv run meeting` 起動である以上、配布先にも uv と workspace が必要になる。
`uv sync` によって Unit B も同じ `.venv` に入るため、CPython を同梱しても使われない。
配布物（`dist/`）が担うのは、.NET 側を配布先の SDK 非依存にすることに限る。
Unit B の実行時には `OUTPUT_DIR` に `[paths]` の出力先を注入し、段の検知と Unit B の出力先を一致させる。

## サブコマンド

ターミナルからは次のサブコマンドを使う。

| コマンド | 役割 |
|----------|------|
| `meeting record [分]` | 録音を開始する（別ターミナルで実行） |
| `meeting stop` | 停止ファイルを作成して録音を止める |
| `meeting live` | ライブ字幕を開始する（確定字幕を JSONL 永続化） |
| `meeting status [session]` | セッションの現在段を表示する |
| `meeting minutes [session] [--claude]` | 議事録パイプラインを見積 → 実行 → 台帳記録する |
| `meeting process [session] [--claude] [--channel <id>]` | 録音済みから議事録・Slack 投稿までを対話 1 コマンドで駆動する（後処理ウィザード） |
| `meeting slack [session] --channel <id>` | 生成済み議事録を Slack へ投稿する |
| `meeting cost [--month YYYY-MM]` | コスト台帳の月次サマリを表示する |
| `meeting tui` | 画面操作（TUI）で一連の操作を行う |

`minutes` は「見積 → 自動実行 → `cost-ledger.jsonl` へ追記 → 閾値警告」を行う。
`--claude` を付けると Claude 生成経路（`--no-summarize`）になる。

## コスト台帳

課金（Transcribe／Bedrock）と PII 送信（Claude 経路）は自動実行できる。
ただし `minutes` は実行のたびに概算を `tools/meeting/cost-ledger.jsonl`（追記のみ）へ記録する。
台帳のパスは環境変数 `SUBTEXT_MEETING_LEDGER` で差し替えられる（テストや別環境向けの継ぎ目）。
単発または月次の累計が閾値（既定は単発 5 ドル・月次 50 ドル、`meeting.toml` の `[thresholds]`）を超えると警告する。
警告のみで処理は止めない。
Claude 経路では `piiSent:true` を必ず残す。
金額は概算であり、正確な請求額は AWS Cost Explorer を正とする。
単価は `meeting.toml` の `[pricing.*]` に、概算に使う換算係数（1 トークンあたり文字数・要約の出力トークン見込み）は同じファイルの `[estimation]` に外出しする。
改定時はこのファイル 1 か所を更新する。

記録する段は `transcribe` / `correct` / `bedrock` / `claude` の 4 種である。
既定経路（Bedrock 生成）は要約の前に C2 用語補正段でも Bedrock を呼び、そこにも全文を送るため、
補正を数えないと 1 回の実行で発生する Bedrock 支出の半分近くが見積・台帳・閾値判定から漏れる。
補正段を踏んだかどうかは `final_transcript.json` の `modelInfo.correction.status` で判定する（`skipped` は未課金）。

台帳への記録は `minutes` だけではない。
TUI の取込も同じ台帳へ追記し、閾値を判定する。
VTT の取込は LLM 段（補正・要約）の概算のみ（Transcribe を経ないため）、mp4 の取込はさらに Transcribe を追記する。
mp4 は録音マニフェストを持たないため、Transcribe の見積根拠となる尺は `ffprobe`（ffmpeg 同梱）で測る。
尺が取れないときは見積が出せないため、課金段（変換）へ入らずに中止する。
金額不明のまま課金することは台帳必須の方針に反するためである。

### 課金と記録を乖離させないための規則

追記は**パイプラインの成否に関わらず**行う。
途中で落ちてもそこまでの AWS 課金は発生しており、成功時しか記録しなければ「課金したのに台帳に無い」状態が生まれる。
一方で無条件に積むと、資格情報エラーなど課金前に落ちた実行にも幻の金額が入り、月次累計と閾値警告を汚す。
そこで段ごとの痕跡を根拠にする（Transcribe は `raw_transcribe.*.json`、補正は上記の補正メタ、要約は `minutes.md`）。
痕跡が残らない失敗（ジョブは完了したが結果取得で落ちた等）は判定できないため、その旨を警告して Cost Explorer での確認を促す。

### 既定セッションの解決順

セッション ID の名前空間は 2 系統（録音は `yyyyMMdd-HHmmss`、取込はファイル名の stem）が混在する。
そのため名前の文字列比較で「最新」を決めると、英字始まりの stem が必ずタイムスタンプに勝つ。
`live_captions` や `Recording` のディレクトリが一度できれば以降の既定は常にそれになり、`meeting slack` が別会議の実名入り議事録を投稿してしまう（外部公開は取り消せない）。
そこで、セッションを省略したときの対象は名前ではなく**実体の最終更新時刻**が最も新しいものとする（同時刻はセッション ID で決定的に並べる）。

## Slack 投稿

Slack 投稿はハーネスに含む（`meeting slack`、`process` の末尾）。
親メッセージに構造化サマリ（タイトル・日時・参加者・決定事項・主な ToDo・脚注）を、スレッド返信に全文を分割して投稿する。
タイトルは議事録先頭ヘッダー（BR-SUM-09）の会議名を使い、無ければセッションIDから作る日時ラベルにフォールバックする。
日時・参加者も同ヘッダーからそのまま転記し、親メッセージだけで「いつ・誰の・何の会議か」が分かるようにする。
Bot Token は環境変数、次にルート `.env` の `SLACK_BOT_TOKEN` の順で解決し、値はログに出さない（BR-SEC-01）。
既定チャンネルは `meeting.toml` の `[slack] default_channel` に置くが、共有・fork される追跡ファイルのため特定チャンネル ID は直書きせず、実行時に `--channel` か対話で与える。

Slack は外部公開であるため、投稿前にプレビューと人間の承認を必須とする（CLI は y/N、TUI は専用モーダル）。
GFM から Slack mrkdwn への変換を含む（見出し・太字の記号寄せ、箇条書きは `•`、チェックボックスは完了/未完了を区別して `☑`/`☐` に変換する）。
見出し前には変換時に必ず空行を1行入れ、元の Markdown で空行が省かれていてもセクション同士が詰まって
見えないようにする。
この経路は Claude／Anthropic を経由せず、PII は自社内と Slack のみに留まり課金もない。

親メッセージが決定事項・ToDo を全文相当で表示するため、スレッド全文はこの2セクションを除いて投稿する
（重複防止。除いた場合は「上の要約メッセージをご覧ください」の注記をスレッド冒頭に添える）。
プレビュー（`_confirm_and_post`）も実際の投稿と同じ入力を使い、承認前に見た内容と実際に投稿される内容が
ずれないようにする。

`/subtext-slack`（Claude 生成の代替経路）はこの変換コードを通らない。Claude がメッセージ本文を組み立てるため、
同じ mrkdwn 変換ルール（見出し→太字、`**`→単一 `*`、箇条書き→`•`、チェックボックスの完了/未完了区別）を
コマンド側の指示として明文化し、経路によって体裁が変わらないようにする。

投稿は途中で諦めない。
全文スレッドは待機を挟んで連投し、レート制限（`ratelimited`）は `Retry-After` に従って有限回だけ再試行する。
途中で失敗するとスレッドが半端に公開されたまま残り、しかも再実行は親メッセージから重複するためである（取り消せない）。
HTTP エラー応答は本文を読んでから扱う（`HTTPError` は `URLError` の派生なので、接続失敗として先に捕まえると 429 の理由と `Retry-After` の両方を失う）。

## 画面操作（TUI）

同じ操作を画面で行う TUI が `meeting tui` である（Textual 製）。
実装は責務ごとに分かれる。
`tui.py` がキー／ボタンの受け取り・一覧と状態の描画・ログ・ワーカー起動を持ち、
表示部品と段の状態計算は `tui_view.py`、モーダル 4 画面は `tui_modals.py`、
録音プロセスの起動・停止は `tui_recording.py`（Textual 非依存）、
取込から命名ゲートを経て議事録へ至る進行と経路の記憶は `tui_minutes.py` にある。
セッション一覧・録音の開始／停止・議事録生成・取込（VTT／mp4）・Slack 投稿・セッション削除を画面から操作できる。
議事録生成と取込は、ボタンとキー操作が Bedrock 経路に固定で、Claude 経路はコマンドパレットからのみ選べる。

取込はファイルの拡張子で経路を振り分ける。
`.mp4` は mp4 取込段（FR-18）を通してから VTT 経路（FR-17）へ接続し、それ以外は VTT を直接取り込む。
ボタンを 2 つに分けないのは、操作者から見れば「会議のファイルを渡す」1 つの操作でしかないためである。

TUI は runner・pipeline・slack へ委譲する薄いフロントで、課金見積と Slack 投稿前の承認は CLI と共通である。
Slack の承認は y/N ではなく専用モーダル（チャンネル入力とプレビューを 1 画面にしたもの）で行うが、投稿関数が人間の承認を必須引数として要求する境界は CLI と同じである。

話者名ゲートは、記入手段が CLI の対話入力に対して TUI では専用モーダルになる。
記入対象の抽出と書き戻しの規則は `naming` に集約し、両者で共有する。
対象は「空欄の others ラベル」と「**自動補完されただけで人が確認していないラベル**」で、確認済みの実名と `self` は温存する。
値が入っていることを確認済みと解釈しないのは、VTT/ライブ字幕由来のヒントが実名とは限らないためである
（ライブ字幕は Unit C の表示ラベル「自分」「相手」、Teams は「Speaker 1」のような仮名を出す）。
値の有無だけでゲートを通すと、参加者全員が仮名 1 人に統合された議事録が黙って出来上がり、TUI はモーダルも出さずに課金段を再開してしまう。
区別は Unit B が `speaker_names.json` に書く `_hintedLabels`（自動補完したラベルの一覧）で行う。
UI は候補を入力欄の初期値として提示し、空入力は「候補のまま確定」として扱って `_hintedLabels` から外す。
命名待ちで停止するとモーダルが自動的に開き、記入して続行すればそのままパイプラインを再開するため、記入と再開は TUI 内で完結する。
無確認の自動記入はしない（FR-H2-03）。
空欄のまま続行することもでき、その場合は `spk_n` のラベルが議事録に残る。
自動再開は 1 セッションにつき 1 回までとし、段が進まないときはモーダルと実行を繰り返さずに次手順の案内へ落とす。

再開に必要な引数は経路によって異なる。
録音由来は `--mode paired` で録音ディレクトリから導出できるが、取込由来は元の VTT パスが必要なため TUI が保持する。
保持はプロセス内に限り永続化しないので、TUI を再起動した後は取込からやり直す（その旨を案内する）。
mp4 由来のセッションで保持するのは変換後の VTT であり、mp4 ではない。
再起動後に mp4 を再指定した場合も、変換済みの VTT があれば変換を起動せずそこから続ける（Transcribe を再課金しない）。
`subtext-mp4-to-vtt` 自身も既存の出力 VTT を上書きせず課金前に停止する（Teams は録画 mp4 と実名入り VTT を同じフォルダへ出すため、上書きは実名入りトランスクリプトの喪失を意味する）。
意図した再変換は `--force` で明示する。

実名と代表発言（PII）はモーダル内にのみ表示し、ログには記入件数だけを書く（BR-NAME-04）。

### 一覧に出す処理状態

セッション一覧は「今どのセッションが動いているか」を行の先頭で示す。
通し番号（`#` 列）の頭にマーカーを置き、録音中は `●`（`$mt-rec`）、それ以外の処理中は `◐`（`$mt-accent-soft`）にする。
待機中の行は空白 2 文字で埋める（マーカーの有無で桁がずれると列全体が動いて読みにくい）。
マーカーだけでは録音とそれ以外しか区別できないため、種別は `段` 列の文字（`議事録生成中` など）で示す。
赤は録音中に限る（`$mt-rec` は他の状態やアクセントに流用しない）。

マーカーは点滅させる。
消灯側は中抜きの丸（`○`）にして色は残す（消えるのではなく脈打って見える）。
`●`／`◐`／`○` はいずれも 1 セル幅なので、点滅で列幅も番号の桁も動かない。

点滅は ANSI の blink 属性（SGR 5）ではなく**タイマーでセルを差し替えて**作る。
blink 属性は端末（Windows Terminal 等）の設定次第で無視され、環境によって点滅しないことになるためである。
動いているセッションが無い間は位相を進めない（待機中の一覧を再描画し続けない）。
処理が現れた瞬間は必ず点灯から始める（消灯位相で現れると待機の丸に見える）。

一覧の `DataTable` は `cursor_foreground_priority="renderable"` で作る。
既定（`"css"`）では `.datatable--cursor` の `color` がセル自身の色を上書きするため、**選択行のマーカーだけ色が消える**。
録音開始時は当の録音セッションを選択状態にするので、既定のままでは色がいちばん必要な行で出ない。

処理中の把握には 2 系統の情報が要る。

- **録音**：`RecordingController` が持つセッション ID。recorder が起動直後に stdout へ出す `sessionId=` の機械可読行から取る（Unit A の既存契約。[03-unit-a-録音.md](03-unit-a-録音.md)）。ID の書式（`yyyyMMdd-HHmmss`）に一致しない行は採用しない。
- **議事録・取込・共有**：ワーカーの起動と終了で登録・解除する。

後者は「セッション ID → 状態」ではなく **ワーカーグループ → セッション ID** で持つ。
セッション ID を鍵にすると、ワーカーが例外終了したとき戻り値（`(session_id, rc)`）が無いため解除できず、処理中の表示が永久に残る。
グループは `Worker.StateChanged` に必ず載るので、終端状態で確実に消せる。
登録は「ワーカー起動と同時」に限り、経路ごとに散らさない。

録音中のセッションは一覧の母集団に入らない。
`manifest.json` が録音**終了時**に書かれるため、進行中のセッションは録音ディレクトリにも `data/out/` にも痕跡を持たないからである。
そこで TUI 側で合成行として挿入する（`runner.list_sessions` は変えない）。
`list_sessions` の母集団へ manifest 無しのディレクトリを入れると `resolve_session` の既定セッションが録音途中のものになり、CLI の `minutes`／`slack` が manifest の無いセッションを掴む。
合成行は永続化せず、段の表示も `STAGE_LABELS` を使わない（`Stage` に値を足すと CLI の `status` と wizard まで波及するため、TUI ローカルに留める）。

検知できるのは TUI 自身が起こした録音だけである。
別ターミナルの `meeting record` は別プロセスで stdout を読めないため対象外とする。

録音を開始したら、一覧を更新して**新しいセッションを選択状態にする**。
これをしないと前のセッションが選ばれたまま残り、停止直後に議事録生成を押すと別の録音へ課金する。
同じ理由で、選択中が録音中のセッションのときは議事録生成を拒否する（取込由来と誤判定して「取込ファイルを保持していません」と案内してしまうため）。

### パイプライン段の注記

段（`#pipeline`）の注記は、段ごとに**自分の状態**を述べる。

| 段 | 完了 | 対象 | 未着手 |
|----|------|------|--------|
| 01 録音 | 録音済（取込由来は「録音なし」） | 未録音 | - |
| 02 取込 | 文字起こし済 | 文字起こし未実行／話者名の記入待ち | - |
| 03 議事録 | 議事録生成済 | 議事録未生成 | - |
| 04 共有 | 共有済 | 未共有 | - |

以前は「現在段のラベル（`STAGE_LABELS`）を対象段にだけ載せる」実装だった。
`STAGE_LABELS` の文言は完了した状態を述べる文（「議事録生成済」）なので、それをまだ終わっていない段に載せると、`minutes_done` のとき **04 共有の下に「議事録生成済」**と出て共有が済んだように読める。
段ごとの注記に変えると、完了した段には完了の事実が残り、対象段には次に必要なことが出る。

「録音済」を出すのは録音由来のセッションだけである（`self_sec` が `None` の取込由来で出すと嘘になる）。
話者名の記入待ちは 02 の対象注記として残す（課金の停止点であり、消してはならない表示である）。
選択中セッションで処理が動いているときは、対象段の注記に「（実行中）」を付ける。

### AWS 認証の確認と表示

起動時に AWS の疎通と認証を確認し、profile・region とともにステータスバーへ出す。

Unit B は課金段の直前に同じ確認を行うが（FR-H2-07）、それでは**録り終えてから失効を知る**ことになる。
会議前に分かるようにするのがここの目的である（FR-H2-11）。

ハーネスは boto3 を持たない（依存ゼロの原則）。
Unit B の `auth_policy` を import することもできない（FR-16：連携はプロセス起動と保存ファイルに限る）。
そこで `uv run subtext-postmeeting --check-auth` を起動し、stdout の `authProfile=` / `authRegion=` / `authStatus=` を読む。
認証の分類と対処メッセージの正本は Unit B 側に 1 つだけ置く。

確認は起動をブロックしない。
ワーカースレッドで実行し、結果が返るまでは「確認中」と表示する（ネットワーク不通で画面が出ないのは事故である）。
応答が返らない場合に備えてタイムアウトを設ける。
失効時は Unit B の対処メッセージをログへ出し、`a` キーで再確認できるようにする。
再認証そのもの（`aws sso login` 等）はハーネスから起動しない。
対話ログインはブラウザと標準入力を使うため、stdout をパイプで受ける TUI 内では入力待ちのまま固まる。

使うプロファイルは `--profile` で切り替えられる（`minutes` / `process` / `live` / `tui`。AWS を触らない `record`・`stop`・`status`・`cost`・`slack` には付けない）。
解決順は `--profile` → 環境変数 `AWS_PROFILE` → ルート `.env` → 未設定（SDK 既定）で、決まった値は子プロセス（Unit B・mp4→VTT・Unit C）へ `AWS_PROFILE` として注入する。
ハーネス自身が `.env` を読むのは Unit C のためである（Unit C は `.env` を読まず、設定は `appsettings.json` と `SUBTEXT_` 接頭辞の環境変数だけなので、注入しないとライブ字幕だけ別のプロファイルで動く）。
未指定時に `default` を明示しない理由は [04-unit-b-会議後パイプライン.md](04-unit-b-会議後パイプライン.md) の「AWS プロファイルの選択」を参照する。

プロファイルの切り替えは課金先アカウントと PII の送信先が変わる操作である。
そのため実行時に使ったプロファイルをコスト台帳へ残す（`profile`）。
台帳は追記のみなので、過去行にこのキーが無いことは正常として読む。

表示は profile と region に限る（例: `AWS default/ap-northeast-1 ✓`）。
アカウント ID・ARN は Unit B が出さないので表示もログもされない（BR-H2-AUTH-04）。
失効表示に `$mt-rec` は使わない（録音中であることだけを示す専用色のため）。

### 外部由来の文字列を画面に出すときの制約

Textual は `[...]` をスタイルタグとして解釈する。
ASCII だけで構成された角括弧（`[TODO]`、`[ap-northeast-1]` など）は**黙って消え**、`[/]` はレイアウト時に MarkupError を送出してアプリを落とす。
和文タグ（`[検討]`）や数字始まり（`[2026-06-01]`）は素通りするため、気づかないまま残りやすい。
`rich.markup.escape` は小文字始まりのタグしか対象にせず Textual の解釈範囲と一致しないので、エスケープでは防げない。

したがって、議事録・ファイルパス・セッション ID のように**外部由来の文字列を表示するウィジェットではマークアップ解釈を無効にする**。
`Static` は `markup=False`、`DataTable` のセルは `str` ではなく `Content` を渡す。
ロゴだけはマイク部分の着色にマークアップを使うため無効にできないので、パスとバージョンを `$変数` の置換で流し込む（置換値は再パースされない）。

`Content` を渡す代償として、その列は Textual の自動幅計算から外れる（`Content` は
`__rich_measure__` を持たないため 1 セル幅と見なされ、列がヘッダ幅のまま潰れてセッション ID が
`20260804-1` のように切れる）。したがって一覧の列幅は内容から自前で算出し、`add_column(width=…)`
で固定する。処理中の表示はセルの差し替えで入るため、その文字列も幅の算出に含める。

これは体裁の問題に留まらない。
Slack 投稿前のプレビューで文字列が消えると、投稿本文には残っているため「見たものと送るものが違う」状態になり、人間承認そのものが意味を失う。
削除確認では「何を削除するのか」が見えないまま承認させることになる。
セッション一覧やステータスバーで名前が消えると、操作者が対象を選べない。

ライブ字幕の開始だけは TUI の対象外とし、`meeting live` をコマンドで叩く。
録音・ライブ字幕は実機 WASAPI を掴むため、TUI からの録音も通常のターミナルで起動する必要がある。

TUI は長時間のブロッキング処理（Transcribe／Bedrock 呼び出し、Slack HTTP、録音 exe 起動）をワーカースレッドで実行し、UI を止めない。

ワーカーの例外はアプリを落とさず、1 行のエラーとしてログへ落とす。
これは利便性だけの話ではない。
Textual の既定ではワーカー内の例外がそのままアプリを落とし、クラッシュ画面が各フレームの局所変数をダンプするため、Slack Bot Token のような秘密が画面に出てしまう（BR-SEC-01、NFR-SEC-04）。
存在しないチャンネル ID を入力したときに実際にこれが起きたため、全ワーカーを「例外でアプリを終了しない」設定で起動する。
録音は `subprocess.Popen` で非ブロッキング起動し、標準出力をパイプで受けてログへ流す。
停止は既存の停止ファイル機構を使う。
TUI 終了時に録音が進行中なら、停止ファイルを作ってプロセス終了を待ち、必ず止めてから閉じる。
待ち時間は最大 15 秒で、それを超えたらプロセスを強制終了する。
この経路では `finally` の flush が走らないため、manifest が不完全になりうる。

実行中のボタンはキャプションで示す（「録音開始」→「停止」、「議事録作成」→「議事録作成中」、「取込 VTT/mp4」→「取込中」）。
無効化はしない（既存のガードが理由をログへ返すため、淡色化してキャプションを読みにくくする方が損である）。
どちらのボタンを押したかは、進行中の処理の種別（`Activity`）で判定する。
ワーカーグループでは判定できない。取込由来セッションで議事録生成を押すと `--mode vtt`（取込と同じグループ）で走るためで、グループを根拠にすると議事録生成中に「取込中」と表示してしまう。

操作は固定キーバインド（`r`＝録音、`i`＝取込（VTT／mp4）、`m`＝議事録、`s`＝Slack、`x`＝削除、`a`＝AWS 認証の再確認、`Ctrl+R`＝再読込、`Ctrl+L`＝ログ全画面、`q`＝終了）とボタンの双方から行える。
なお内部の識別子（`action_import_vtt`、ウィジェット ID の `import-vtt`）は VTT 専用だった当時の名残であり、実際は mp4 も受け付ける。
パイプラインの段は「録音・取込・議事録・共有」の 4 つで表示する。
共有済みのマークは画面内の状態にとどめ、永続化しない。
配色トークンは `tools/meeting/meeting/app.tcss`（接頭辞 `$mt-`）に定義する。

## Claude Code との連携

会議ハーネスは H2 を実装したものだが、狙いに掲げた「Claude Code をオーケストレータとする」形からは配置が変わっている。
段の駆動・状態検知・課金実行・台帳記録はハーネスが持ち、Claude は判断段（話者名の提案・議事録の文章化・Slack 文面）に専念する。
実行境界の原則は次のとおりである。

- 実機 WASAPI を掴む録音・ライブ字幕は、ユーザー本人が通常のターミナルで叩く。Claude セッション内からは起動できない。
- 停止ファイルの作成や整合チェックは Claude が実行してよい（無害）。
- Slack 投稿は Claude が実行してよいが、外部公開のため宛先と内容を必ず事前確認する。

H2 の要件と検討の経緯は [08-追加機能.md](08-追加機能.md) を参照する。
