# 追加機能の設計と現状

PoC の実現性検証を通過したのち、自分専用の実用ツールとして堅牢性・機能・精度を高める段階に入った。
この段階の機能は、いずれも PoC の設計判断（fail-fast の一括停止、非永続化）を意図的に上書きする。
本章は各機能の狙い・要点・現状をまとめる。

着手順は、実測の課題に沿って再接続耐性（A1）と対話駆動オーケストレーション（H2）を先に、用語精度（C1 → C2）を後にした。

## A1：ライブ字幕の再接続耐性

### 狙い

PoC の Unit C は「単発・正常系・全停止」を前提にしていた。
片系統が 15 秒無音になると Transcribe の idle timeout で接続が切れ、fail-fast（BR-ERR-03）が両系統を巻き込んで全停止する失敗モードがあった。
A1 はこれを、系統ごとに自動再接続し、片系統が恒久障害でも生存系統を継続する設計へ変える。

### 要点

- 例外を一過性（transient）と致命（fatal）に分類する（BR-RECONN-01）。未知の例外は安全側の transient に倒す。
- 再接続待機はフルジッタの指数バックオフで行う（BR-RECONN-02）。`CancellationToken` で即中断できる。
- 再接続予算（既定 5 分のウィンドウ）を超えたら恒久障害と判定し、当該系統のみ停止する（BR-RECONN-03）。字幕の受信成功でウィンドウをクリアする。
- 15 秒の idle timeout を避けるため、無音 PCM を注入する（FR-A1-05）。
- 再接続後のオフセットは、新しいストリーミングセッションの相対時刻として 0 起点に戻る（FR-A1-06）。表示層は境界マーカー行を出して新旧セッションの混線を読み手に明示するにとどめ、final の重複除去は行わない。

fail-fast の反転は設計の根幹に触れるため、欠落区間の扱いと重複字幕に新たな複雑性が生じる（確信度：高）。

### 現状

実装済み・クローズ（2026-06-25、実 AWS 受け入れ GO）。
`ReconnectPolicy`（純粋関数群）と `LiveSttApp` の系統独立化で実現した。

## C1：カスタム語彙

### 狙い

固有名詞・人名・専門用語の誤認識を、Transcribe の Custom Vocabulary で是正する。
git 管理の用語ファイルと冪等な投入スクリプトで、Unit C（ストリーミング）と Unit B（バッチ）の双方へ同一の語彙名を配線する。

### 要点

- Unit C は設定 `Live:VocabularyName`、Unit B は環境変数 `VOCABULARY_NAME` で語彙名を参照する（FR-C1-01／02）。両ユニットは語彙名を各自の設定で独立に参照し、語彙そのものは共有しない（BR-VOCAB-01）。
- 用語ファイルは TAB 区切りの table 形式で持つ（FR-C1-03）。ヘッダは `Phrase`／`SoundsLike`／`IPA`／`DisplayAs` の 4 列が必須である。日本語で使えない `SoundsLike` と `IPA` も、空欄の列として置く。
- 投入は冪等（Create / Update）で行い、READY を待ち、FAILED なら非ゼロ終了する（FR-C1-04／05）。

### 現状

実装済み・クローズ（2026-06-26、採用したが主役から降格）。
実 AWS の検証で本質的な限界が判明した。
日本語（ja-JP）は Phrase と DisplayAs のみに対応し、`SoundsLike` と `IPA` が廃止されている。
そのため、ASR がローマ字で出力する英語系固有名詞（例：BeeX が `bx`、Bedrock 系の誤り）は原理的に救済できない。
効くのはカタカナ固有名詞に限られる（ベストエフォート）。
配線とツールは健全なので削除せず後方互換を保ち、固有名詞強化の本命は C2 に移した。

## C2：LLM 後処理補正

### 狙い

ASR 出力の後段で、LLM（Bedrock）と決定的辞書を用いて、用語リストに沿った固有名詞の表記を是正する。
ASR の音響認識に依存せず文脈で訂正できるため、C1 の構造的限界を超える。

### 要点

- 段の構成を `NAMED → CORRECTED → SUMMARIZED` に拡張する（FR-C2-01）。`final_transcript.json` は補正後で確定し、補正前は `final_transcript.named.json` に原文保持する（BR-CORR-04）。
- 既定で有効。`--no-correct` で無効化でき、無効時は非課金（FR-C2-02）。`--no-summarize` を指定した場合も補正段を自動でスキップする。
- この自動スキップは、Claude 生成経路（`meeting minutes --claude`）を常用すると**用語補正が一度も効かない**ことを意味する。課金ゼロを優先した設計判断だが、固有名詞の表記は補正されないまま Claude へ渡る。この経路で表記を揃えたい場合は、`final_transcript.json` を読ませるときのプロンプトで用語リストを併せて与えるか、`--no-summarize` を使わず要約段まで Bedrock に回す。
- 補正は用語リストにある固有名詞の誤認識のみを正規表記へ訂正する（BR-CORR-02）。リストに無い語・文構造・句読点・助詞は一字一句変えない。
- セグメントの `text` のみを変更し、セグメント数・時刻・話者は不変とする（BR-CORR-01、構造不変）。
- 決定的辞書と LLM の二段構成で、LLM が失敗しても辞書分の補正は維持する（FR-C2-07）。フェイルセーフは、LLM 応答が崩れたら不採用に倒して辞書適用済みを採用し、警告する挙動である（NFR-C2-03）。
- Bedrock の呼び出しは 1 セッションあたり 1 回に抑える（NFR-C2-01）。
- 録音経路と VTT 経路の双方で、`final_transcript.json` の確定前に適用する（FR-C2-04）。

語境界の規則を持つ（BR-CORR-06）。
ASCII エイリアスは前後を英数字で挟まれない位置でのみ置換し、部分文字列の誤爆を防ぐ。
和文エイリアスは最長一致を優先する。
ただし和文には語境界の概念が無く素朴な部分一致になるため、**3 文字未満の和文エイリアスは読込時に拒否する**。
同梱していた 2 文字の「イジ」（`1G` のエイリアス）は「エンゲイジメント」「ペイジ」「デイジー」の内側に一致し、
決定的・非課金で既定経路では必ず通る辞書段が、`final_transcript.json` → 議事録 → Slack まで壊れた本文を流していた。
短い誤認識は辞書段ではなく LLM 段（文脈を見る）に任せる。

用語ファイルの読込は設定ミスを早期に顕在化させる（NFR-C2-03）。
`aliases` を配列でなく文字列で書いた場合（`"aliases": "bx"`）は 1 文字ずつのエイリアスに展開されてしまうため、書き方を示して停止する。
正規表記は `re.sub` の置換テンプレートとしてではなくリテラルとして扱う（バックスラッシュを含む表記で課金後に例外にならないようにする）。

### 現状

実装済み・クローズ（2026-06-26、実 AWS 受け入れ全 GO）。
`correction.py` と用語ファイルで、合成 VTT に対し `bx → BeeX`・`ベトロック → Bedrock`・`イチジー → 1G` の是正と構造不変を実証した。
既知エイリアスは辞書段（決定的・非課金）だけで全件是正され、LLM 段は安全網として機能した。

## H2：Claude-as-frontend

### 狙い

Claude Code をオーケストレータ兼出力ルーターとし、自然言語の対話で「録音 → トランスクリプト・議事録 → Slack 投稿・Obsidian 保存」を単一利用者・手動起動で完遂する。
新規インフラはほぼ持たず、会議への非参加を維持する。

### 要点

- 対話駆動でオーケストレーションしつつ、ユニット間の疎結合を維持する（FR-H2-01）。
- 停止は停止ファイルを正本とし、`manifest.status=complete` を保証する（FR-H2-02）。シェル経由の kill は Git Bash 環境で `manifest` を生成できないため使わない（後述のスパイクを参照）。
- 話者名は Claude の推論案をユーザーが承認・修正してから記入する（FR-H2-03、BR-H2-NAME-01）。無確認の自動記入はしない。
- Slack 投稿は投稿先チャンネルとドラフト本文を提示し、承認後にのみ送る（FR-H2-05、BR-H2-SLACK-01）。本文は要約・議事録に限り、生の文字起こしは貼らない。
- 課金段（Transcribe／Bedrock）に入る前に認証情報の有効性を確認する（BR-H2-AUTH-02）。失効時は再認証後に冪等再開し、既存成果物を再利用して再課金しない（BR-H2-AUTH-01）。自動リトライは一過性障害のみ・有限回とし、恒久障害は即停止して通知する（BR-H2-AUTH-03）。
- いかなる終了経路でも、`KEEP_S3=true` でない限り当該セッションの S3 を掃除する（BR-H2-S3-01）。掃除は冪等・フェイルセーフとする。

### 現状

実装済み・CONSTRUCTION 完了（2026-06-25、実 AWS 受け入れ全 GO）。

実装の主体は会議ハーネス（`tools/meeting`。CLI と TUI）である。
停止ファイルによる停止（FR-H2-02）・話者名ゲート（FR-H2-03）・Slack 投稿の承認（FR-H2-05）は、いずれもここで担う。
Unit B 側は、課金段の前の認証事前チェック（`auth_policy.py`）と、パイプラインの全終了経路での S3 掃除で支える。
設計の詳細は [06-会議ハーネス.md](06-会議ハーネス.md) を参照する。

狙いに掲げた「Claude Code をオーケストレータとする」形は、実装ではターミナル起点のハーネスに移した。
Claude Code は起動と判断の入口として使い、段の駆動と課金台帳はハーネスが持つ。

実機で 2 件の欠陥（Transcribe 例外経路での cleanup 漏れ、認証プロファイル未検出時の生トレースバック）を発見し修正した。

参考として、H1（Slack の予約コマンドからアウトバウンドポーリングで録音を自動起動する方式）は配信軸の別案であり、H2 の最優先化に伴い後続フェーズへ降格・保留とした。

## B1：ライブ議事録

### 狙い

確定したライブ字幕をローカル JSONL に追記し、軽量な Python ワーカーが一定間隔で累積要約（ローリング議事録）を更新する。
最終議事録は B1 では作らず、JSONL から VTT への変換で既存の `vtt` モード経路へ橋渡しする。

### 要点

- 確定字幕（final）のみを JSONL に追記し、クラッシュ安全にする（FR-B1-01／02）。
- ワーカーは累積方式で、既定 5〜10 分間隔でローリング議事録を上書きする（FR-B1-03／04／07）。
- コスト台帳と連携し、閾値超過を警告する（FR-B1-08）。障害時は警告して継続する（FR-B1-09）。
- 対象は 4 面（Unit C の字幕 sink、JSONL から VTT への変換、ハーネスの live 段、Unit B のローリング要約ワーカー）である。

ローリング議事録は LLM 呼び出しの頻度がコストに直結するため、間隔の設計を要する（確信度：高）。

### 現状

4 面のうち下層の 3 面（Unit C の字幕 sink、JSONL から VTT への変換、ハーネスの live 段）は、後述の B1F として実装済みである。
B1 固有の未実装部分は残る 1 面のローリング要約ワーカーだけで、これは Inception 進行中・要件承認待ちである。

## B1F：ライブ字幕の永続化基盤

### 狙い

B1 の下層を切り出した基盤スライスである。
永続化と起動・停止のオーケストレーションまでを範囲とし、ローリング要約ワーカーなどの消費側は載せない。

### 要点

- 確定字幕のみを JSONL に追記する（FR-B1F-01）。
- クラッシュ安全に加え、Windows のファイル共有モードを明示し、同時読み取りで破損しないようにする（FR-B1F-02）。これが B1 との差分で、Windows の同時アクセスという技術リスクを明示化した。
- 停止ファイルで安全停止する（FR-B1F-03）。ハーネスの live 段が subprocess として起動する（FR-B1F-04）。
- JSONL から VTT へ変換し、`vtt` モードへ接続する（FR-B1F-05）。cue の時刻整合を保ち、同時刻は 1ms 単調増加で重なりを避ける（BR-B1F-TIME-01）。
- cue の並びと開始時刻は `captureUtc`（壁時計）を正とする。A1 の再接続では `offsetMs` が新セッションの 0 起点へ戻るため、`offsetMs` だけで並べると再接続後の cue が前方へ回り込む。`captureUtc` を欠く行が混じるときのみ `offsetMs` 昇順に倒し、その場合は再接続をまたいだ順序を保証しない。
- 変換後の実名付与は既存の命名ゲート（`subtext-postmeeting --mode vtt`）で行う（BR-B1F-LABEL-01）。

既知の制約として、確定字幕のみを永続化するため、消費側は字幕確定までの遅延（A1 実測で 2.8〜6 秒）を負う。

### 現状

実装済みである。
Unit C の確定字幕 JSONL sink（`JsonlCaptionSink`）、JSONL→VTT 変換 CLI（`subtext-live-to-vtt`）、および会議ハーネスの live 段で実現し、既存の `vtt` モード（命名ゲート）へ接続する。
